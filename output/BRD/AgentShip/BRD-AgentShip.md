## 1. 背景与目标

AgentShip 是面向 Agent 自动化研发的交付平台，覆盖需求、产品定义、前后端开发、测试和部署发布。用户可以配置流程的阶段、节点、节点依赖及各节点的 Agent，并为新需求或已有需求发起交付运行。用户登录后可查看需求和进度、配置 Agent，并在开发过程中与 Agent 对话。Agent、流程和需求配置均设有主负责人及副负责人角色。

| 目标 | 预期业务结果 |
|---|---|
| OBJ-01 自动化交付 | 需求进入运行后，由 Agent 按用户所选流程推进阶段与节点、传递产物，并完成该流程约定的交付。 |
| OBJ-02 过程可见 | 项目参与者可以查看需求、所处阶段、节点结果及阻塞原因，了解下一步需要做什么。 |
| OBJ-03 人机协作 | 项目参与者可以通过项目内对话补充上下文，并查看、配置参与流程的 Agent。 |

### 成功指标（拟议）

| 指标 | 度量口径 | 基线 / 目标 |
|---|---|---|
| 端到端交付成功率 | 对包含发布的运行，统计达到约定发布目标的运行数 ÷ 同期已结束的运行数。 | 待试点建立基线 / 待确认 |
| 交付耗时 | 对包含发布的运行，统计从用户发起自动化到发布成功的耗时，包含适用的建仓和人工等待时间。 | 待试点建立基线 / 待确认 |
| 每次运行的人工推进次数 | 统计为继续执行所需的人工操作，如确认、恢复和重试，按操作类型分别统计。 | 待试点建立基线 / 待确认 |

统计窗口、样本范围和指标负责人待确认。暂无交付耗时、成功率或人力投入的基线数据。

## 2. 用户与职责（拟议）

| 角色 | 业务职责 |
|---|---|
| 平台用户 | 注册账号，并通过邮箱或用户名登录后进入 AgentShip 业务页面。 |
| 项目发起者 | 填写新需求名称或选择已有需求，再确定工作类型和流程，发起自动化交付并查看运行结果。 |
| 项目协作者 | 查看需求与看板，在开发过程中与 Agent 对话并补充上下文。 |
| 项目维护者 | 处理仓库、分支或运行异常，并查看运行采用的节点 Agent 配置。 |
| 流程配置者 | 在流程配置入口管理流程、阶段、节点、节点依赖和各节点的 Agent。 |
| 配置主负责人 | 为其负责的 Agent、流程或需求配置添加或移除副负责人，并可转交主负责人身份。 |
| 配置副负责人 | 查看并编辑其担任副负责人的 Agent、流程或需求配置。 |
| 发布与验收相关人员 | 按最终确认的权限和发布规则验收产物或作出放行决定。 |

首期目标用户、各角色权限及具体审批人待确认（DEC-01、DEC-05、DEC-07、DEC-11）。

优先级采用 `Must`、`Should`、`Could` 和 `Won’t for this phase`。下表的优先级、验收口径及交付分期均为草案建议。决策状态标记的是能力是否来自已明确的项目范围，`已确认` 表示范围已明确，文档审批见第 10 节。

| BR-02 | 启动确认后，AgentShip 根据所选需求的仓库关联和工作类型准备 Git 仓库与分支，并将结果关联到本次运行。 | Must | 已确认 | 首期拟议 | 需求尚未关联仓库时，系统自动建仓并关联该需求。需求已关联仓库时，四种工作类型均使用该仓库并按对应规则创建工作分支。已有仓库缺少本次所需的 `dev` 时，系统先从默认分支创建 `dev`，再继续创建工作分支。可核对实际仓库、基准分支和工作分支。Git 准备失败时显示原因，研发阶段等待处理。 |

## 5. 业务流程与规则

### 注册与登录

未注册用户先提交注册资料，密码和确认密码须一致。已注册用户通过邮箱或用户名搭配密码登录。用户登录后方可进入 AgentShip 业务页面。密码为 15～128 个字符，允许空格和符号，两次输入须完全一致。注册后账号待验证，邮箱和手机号都验证成功才激活并允许登录。同一个邮箱、同一个手机号各只能绑定一个账号。邮箱不区分大小写，手机号统一带国家区号判重。

### 管理配置负责人

主负责人和副负责人按单项配置管理，分别适用于 Agent 配置、流程配置和需求配置。创建配置时，系统自动将创建者设为主负责人，这条规则也适用于从启动入口创建需求。主负责人可在其负责的配置中添加或移除副负责人，包括最后一位。配置可以只保留主负责人。副负责人可以查看并编辑其负责的配置。流程副负责人可在自己有权发起的运行中选用该流程，Agent 副负责人可在自己有权编辑的流程中选用该 Agent。移除副负责人时，该角色授予的编辑和使用权立即失效。被移除者在已打开的编辑页提交时，系统拒绝保存并提示已被移除。主负责人可以向其他已注册用户发起转交，包括当前副负责人和未担任该配置副负责人的用户。主负责人提交转交成功时，接任者立即获得主负责人的权限，原主负责人同时退出该配置的负责人名单。添加副负责人和转交主负责人时输入注册用户的用户名。其他操作权限见 DEC-11。

新建需求默认仅创建者可见。当前主负责人通过添加副负责人共享需求。副负责人可在需求列表、详情页和启动时的搜索或下拉列表中看到该需求，并可编辑和保存需求内容。创建者转交需求并退出负责人名单后，系统按新的负责人名单展示需求，原创建者随即失去查看权限。

### 配置流程

流程配置者在流程配置入口创建或编辑流程，为各阶段填写名称，并在阶段下添加多个具名节点。流程配置者可设置同阶段节点依赖，也可为节点设置更早阶段的前置节点，并为普通节点配置 Agent。设置条件分支时，流程配置者须为「通过」和「需修复」两个结果都配置后续路线，才能保存流程。用户可在流程配置中为各检查节点分别设置自动修复次数上限。流程最后必须设置一个用于标记完成的结束节点。保存时，系统检查结束节点和节点依赖，发现循环依赖时提示「有循环依赖」并拒绝保存。保存后的可用流程可在发起运行时选中。

节点进入正常执行后，所配置的多个 Agent 均参与执行。流程配置者可设置它们的执行先后，未设置时默认并行执行。Agent 之间可以交换任务信息，节点内的 Agent 也可以与用户沟通。Agent 发出需要用户回复的问题时，页面显示「等待回复」、回答框和「回复」按钮。发问的 Agent 等待，其他 Agent 可继续执行各自可做的任务。用户填写答案并点击「回复」后，系统将答案发给提问的 Agent，该 Agent 继续执行。待回复问题一直保留到有权限的用户回复，或运行发起人主动取消。关闭和重新打开聊天页后仍可看到待回复的问题。运行发起人取消问题后，提问的 Agent 结束等待，用已有信息继续执行。

所选 Agent 均成功或由人工跳过失败项，且节点最终产物可用后，节点才算完成，依赖它的节点才能继续。产物按节点验收，多个 Agent 可共同产出。阶段按配置顺序执行，上一阶段的所有应执行节点完成后，下一阶段才开始。同一阶段的节点互不依赖且共同依赖同一个上游节点时，在共同上游完成且各自依赖满足后可以并行。有条件分支时，系统读取上游节点产物中的检查结果，执行「通过」或「需修复」对应的一条路线。检查产物缺少有效结论时，页面显示「待人工处理」和原因。当前聊天页操作者可点击「重新检查」，系统重新执行原「检查」节点，获得有效结论后按对应路线继续。多条实际执行的并行路线都通向结束节点时，须等这些路线全部完成后才能到达结束节点。走过「需修复」路线的运行，修复完成后在同一次运行中重新执行原「检查」节点。复查结果仍为「需修复」且未达到配置上限时，系统自动再修一轮并复查。达到上限且仍需修复时，受影响路线等待，无关路线继续。页面显示「待人工处理」及达到上限的原因。复查结果为「通过」才允许发布。每个检查节点独立计算修复次数，首次修复计为该节点的第 1 轮。暂停后，当前聊天页操作者可选择「再修一轮」或「停止本次运行」。再修一轮后仍需修复时再次暂停。运行沿用启动时采用的流程配置，保存后的修改用于新运行。同一阶段多个节点都可开始但没有共同上游时，按配置中的排列顺序逐个执行。交互时点、产物汇总和失败处置细则见 DEC-09。

### 发起运行

1. 确定需求。填写并确认添加需求名称，或通过搜索和下拉列表选中一条已保存的需求。输入的名称与已有需求相同时，系统按用户权限提示选择已有需求或提示该名称不可用。系统读取该需求的仓库关联。
2. 确定工作类型。需求未关联 Git 仓库时按新需求处理，工作类型固定为「新功能」。需求已关联仓库时，用户须手动选择「新功能」「重构」「紧急修复」或「常规修复」。
3. 选择流程。可输入名称搜索或打开下拉列表，从自己有权限使用的可用流程中选中一条。四种工作类型使用同一选择范围。新增或编辑流程通过流程配置入口完成。
4. 确认发起。需求主负责人提交启动。系统先核对发起权限，并检查没有需求阶段的流程所需的描述。校验通过后，系统自动为未关联仓库的需求创建 Git 仓库，并将仓库关联到同一条需求。需求已关联仓库时，系统直接使用该仓库。系统按工作类型准备分支，准备成功后关联到本次运行，再执行所选流程。该次运行的全部 Codex Agent 由发起运行的电脑执行。

| 工作类型 | Git 仓库 | 分支创建规则 |
|---|---|---|
| 新功能 | 使用需求已关联的仓库，未关联时自动新建并关联。 | 已关联仓库时从 `dev` 创建 `feature` 工作分支。新建仓库时先从默认分支创建 `dev`，再从 `dev` 创建 `feature` 工作分支。 |
| 重构 | 自动使用所选需求关联的已有 Git 仓库 | 从 `dev` 创建 `refactor` 工作分支。 |
| 紧急修复 | 自动使用所选需求关联的已有 Git 仓库 | 从默认分支创建 `hotfix` 工作分支。 |
| 常规修复 | 自动使用所选需求关联的已有 Git 仓库 | 从 `dev` 创建 `fix` 工作分支。 |

已有仓库执行新功能、重构或常规修复时，若缺少 `dev`，系统先从该仓库的默认分支创建 `dev`，再从 `dev` 创建本次工作分支。

新仓库由系统创建在用户填写的 GitHub 账号或组织下，默认公开。已关联需求沿用原仓库。分支按固定规则处理，重名细则见 DEC-02。需求文档、代码和可公开的节点交付产物归档到需求关联仓库。账号资料、聊天原文和原始执行日志保存在平台，公开仓库只收录可公开的报告内容。

仓库关联是判断是否按新需求启动的依据。选中一条已保存但未关联仓库的需求时，系统沿用所选需求记录，自动为它创建并关联仓库。

需求名称在启动第一步确定。选择含需求阶段的流程时，描述可在启动后到需求阶段补齐。所选流程没有需求阶段时，必须在启动前补齐描述。完整交付的参考路径为需求 → 产品定义 → 前后端开发 → 测试 → 部署发布。运行看板根据所选流程展示阶段和节点，开发中可进入项目内对话。必测项、人工确认和放行规则适用于相应的交付操作（DEC-04）。

运行状态拟采用「待开始」「执行中」「待人工处理」「失败」「已完成」「已停止」。待人工处理表示仍可在满足条件后继续，失败表示当前尝试以失败结束。看板应能区分两种情况并展示原因。流程到达结束节点时，运行标记为「已完成」。Agent 失败时，页面用简明提示说明哪个 Agent 失败、已确认的原因及可用操作。可重试的 Agent 由当前聊天页操作者点击「重试」，系统只重试失败的 Agent，沿用已完成的结果。发起电脑关机并离线时，运行页面显示「等待发起电脑上线」。原电脑重新上线且 Codex CLI 可用后，系统自动继续同一次运行。原会话不可用时从最近保存的进度继续。当前聊天页操作者也可跳过失败 Agent，节点仍须交付可用产物。外部操作结果不明的处理见 DEC-12。

### 使用聊天页面

运行发起人可进入聊天，也可添加或撤销其他注册用户的本次运行聊天权。同一个聊天页面同一时间由一名有聊天权限的用户在一个浏览器标签页中使用。需求副负责人不能进入该需求已有运行的聊天页或提交回复。当前使用者再次打开同一个聊天时，只有已取得占用的标签页可操作。运行达到自动修复上限并暂停时，当前聊天页操作者可以在该标签页选择再修一轮或停止运行。页面已被占用时，其他用户尝试打开会看到弹窗，弹窗显示当前使用者，系统阻止其操作该聊天页面。聊天页的当前使用者与运行绑定的执行电脑分别记录。当前使用者离开或关闭正在操作的标签页后立即释放占用，其他有权限的用户可进入使用。系统检测到当前使用者断网后，为其保留占用 5 分钟。用户在时限内重连可继续操作，超时未重连则释放占用。正常关闭通知未送达时，也按断连规则处理。

只有在流程已配置且正在执行的 BRD（需求）阶段节点内，才可通过聊天修改本次运行的需求。确认前沿用已生效内容。由运行发起人确认，原需求与本次运行同步更新。尚未开始的节点采用新版本。已在执行的节点按原版本完成，结果标记为「基于旧版本」。已完成的节点默认保留，由发起人决定是否重跑受影响节点。

| Agent 运行能力 | 按流程节点配置处理需求与上游产物，支持 Agent 之间交换任务信息以及与用户沟通，返回节点结果和对话回复。 | Agent 不可用时，受影响节点保留状态并说明原因。 | Agent 配置权限和使用边界见 DEC-05，节点内多 Agent 协作规则见 DEC-09。 |
| 用户本机 Codex CLI | 接收 AgentShip 对话对应的输入，执行采用 Codex CLI 的 Agent 会话并返回回复。 | 发起电脑关机后运行等待原电脑上线，原电脑及 CLI 恢复可用后继续同一次运行。 | 本机接入前提和中断步骤的恢复细则见 DEC-12。 |
| 测试与部署发布能力 | 对本次代码执行测试，并将符合发布条件的产物部署至指定环境。 | 记录测试或部署失败及其影响，保留可供后续处理的结果。 | 测试范围、目标环境和发布权限待确认（DEC-03、DEC-04）。 |

## 8. 风险与影响

| 风险 | 影响 | 拟议处理 | 责任人 |
|---|---|---|---|
| 需求通过对话补充后，后续阶段仍引用旧内容。 | 产物偏离需求，测试可能以错误口径验收。 | 确认变更后可追溯，并明确已经执行的阶段是否需要重跑。 | 待确认 |
| 建仓、建分支或部署的外部结果返回超时。 | 重复创建仓库或分支、重复执行发布，或看板状态与实际结果不一致。 | 将结果不明的操作置于待处理状态，核对实际结果后再决定是否恢复。 | 待确认 |
| 测试或发布条件不足以验证试点结果。 | Agent 可能交付不可用的产物，或发布至未经确认的环境。 | 试点前明确必测项、发布环境和放行责任。 | 待确认 |
| 对话、配置或产物的访问范围不清晰。 | 项目内容被无权限人员访问，或进入超出授权范围的 Agent 处理流程。 | 在试点启动前确认角色、数据使用边界及留存规则。 | 待确认 |
| 流程配置在运行期间发生变化。 | 看板、实际执行和验收依据可能产生分歧。 | 拟保留每次运行采用的阶段、节点、依赖和 Agent 配置，流程变更用于后续运行（DEC-07）。 | 待确认 |
| 节点依赖互相等待，或多个 Agent 的结果无法形成节点结论。 | 运行可能停在当前节点，后续依赖节点无法推进。 | 在试点前确认依赖校验与满足条件，以及节点内多个 Agent 的完成判定（DEC-07、DEC-09）。 | 待确认 |
| 注册资料可见范围不清晰。 | 姓名、手机号码或邮箱可能被无权限人员查看。 | 试点前确认资料可见范围和留存规则（DEC-05、DEC-10）。 | 待确认 |
| 副负责人被移除时编辑页仍处于打开状态。 | 已打开的编辑页仍可能提交旧权限下的修改。 | 保存时按当前权限校验，拒绝被移除者的修改并显示原因（UAT-18）。 | 待确认 |

## 9. UAT 与验收（拟议）

首期在开发环境验证。正式发布和生产放行场景留待后续。

| 场景 | 验收结果 | 关联需求 |
|---|---|---|
| UAT-01 新需求从启动到开发交付 | 填写并确认添加需求名称，核对工作类型固定为「新功能」，选择已配置的完整交付流程。启动后核对系统自动创建仓库并关联该需求，再从默认分支创建 `dev`，再从 `dev` 创建 `feature` 工作分支。Git 准备成功后在开发环境执行流程。看板可查看节点状态，并核对需求关联仓库中的产品定义、代码和测试交付物。 | BR-01～BR-08、BR-13～BR-16 |
| UAT-02 Git 准备失败及恢复 | 分别模拟建仓失败或结果不明、工作分支创建失败或结果不明。研发阶段保持等待，看板显示原因。具备恢复条件时继续同一请求，沿用已完成的仓库和分支结果。 | BR-02、BR-08、BR-11、NFR-03 |
| UAT-03 测试失败或待放行（正式发布部分留待后续） | 必测项失败或适用的发布确认未完成时，发布阶段保持等待，看板可查看原因。满足约定条件后可继续。 | BR-06～BR-08 |
| UAT-04 节点配置多个 Agent | 为同一节点配置至少两个 Agent，保存后重新打开核对。启动运行后可查看该节点实际采用的 Agent。修改流程内节点的 Agent 配置后，可区分前后两次运行采用的配置。 | BR-09、BR-42、NFR-02 |
| UAT-05 开发中与 Agent 对话 | 验证普通聊天及 BRD 节点内的提案。确认前沿用旧内容，非发起人确认被拒绝。发起人确认后原需求与本次运行同步更新，尚未开始节点采用新版本。已在执行的节点按原版本完成并标记旧版本，已完成节点默认保留，发起人可选择重跑受影响节点。无 BRD 阶段或离开该阶段后拒绝聊天改需求。 | BR-01、BR-10、BR-51 |
| UAT-06 节点失败和重试 | 可重试的节点失败时可查看失败原因；具备权限的维护者发起恢复后，原失败结果和重试结果均可查。节点内 Agent 的手动重试权限与范围见 UAT-36。 | BR-08、BR-11、NFR-02、NFR-03 |
| UAT-07 权限隔离 | 无权限人员通过搜索或下拉尝试选择受限需求或流程，或尝试查看受限项目、编辑受限流程和节点 Agent、发起受限发布操作。系统按已确认的权限规则限制访问或操作。 | NFR-01 |
| UAT-08 配置、选择并执行流程 | 在流程配置入口保存两条末尾均包含结束节点的不同流程，至少一条包含多个具名阶段及同阶段下的多个具名节点，分别设置同阶段节点之间的依赖，以及「测试」阶段的节点 B 依赖「开发」阶段的节点 A。保存后重新打开，核对两类依赖及跨阶段节点的所属阶段。另测将「开发」节点配置为依赖更晚的「测试」节点，核对系统提示冲突并拒绝保存。分别通过搜索与下拉选中已保存的流程。启动入口仅能选择流程。运行和看板反映所选配置，跨阶段的 B 在 A 完成后才可开始。 | BR-08、BR-12、BR-15～BR-17 |
| UAT-09 已关联仓库的需求启动运行 | 分别通过名称搜索和下拉列表选中已关联仓库的需求，核对工作类型须手动选择。分别选择新功能、重构、紧急修复和常规修复发起运行，核对四种工作类型均使用该需求已关联的仓库，分别验证 `dev` → `feature`、`dev` → `refactor`、默认分支 → `hotfix`、`dev` → `fix`。紧急修复分别使用默认分支名为 `main` 和 `master` 的仓库验证。运行可追溯所选需求、类型、流程、仓库和分支。 | BR-02、BR-13～BR-16、NFR-02 |
| UAT-10 启动信息缺失 | 分别验证未填写并确认需求名称且未选中已保存的需求、已关联仓库的需求未手动选择工作类型、未选中流程时，系统提示相应缺项且不启动。仅输入已有需求或流程的搜索文字也不满足选择条件。 | BR-13～BR-15 |
| UAT-11 流程修改后的运行追溯 | 启动后修改所用流程的阶段、节点依赖或节点 Agent 配置。验证当前运行继续按启动时的配置执行，历史运行可核对原配置，之后新启动的运行采用修改后的配置。 | BR-08、BR-09、BR-12、BR-16、BR-17、BR-42、NFR-02 |
| UAT-12 注册及校验 | 验证用户名规则、密码 14／15／128／129 字符边界和确认不一致，含空格及符号的长密码可接受。分别验证邮箱大小写变体、同一手机号的不同书写方式及并发重复。仅一个渠道通过仍不能登录，两个渠道通过后可登录。核对注册到期后可用相同标识重新注册，旧验证码无法用于原注册或新注册。开发验收使用本地模拟渠道。 | BR-18、BR-19 |
| UAT-13 登录与页面访问 | 未登录时可打开登录和注册页面，直接打开业务页面须先登录。分别以同一账号的邮箱和用户名搭配正确密码登录，均可进入业务页面。密码错误或账号仅完成一项验证时无法登录。 | BR-20、BR-21 |
| UAT-14 三类配置的负责人管理 | 分别创建 Agent、流程和需求配置，核对创建者自动成为主负责人。再从启动入口新建需求，核对发起者自动成为该需求的主负责人。以主负责人身份添加副负责人并核对名单更新。对三类配置分别验证副负责人可以查看、修改并保存自己负责的配置内容，且仅凭该身份无法编辑未分配给自己的配置。仅持副负责人角色的用户尝试添加或移除他人时，名单不发生变化。对三类配置分别由主负责人移除最后一位副负责人，核对副负责人名单为空且主负责人仍在。 | BR-22～BR-24、NFR-01 |
| UAT-15 账号资料保护 | 验证登录账号可读取自己的邮箱和手机号。其他账号无法从资料、成员列表或接口读取其联系方式。验证首期无后台停用入口。核对业务页面、运行记录及配置变更记录均不显示密码或确认密码。 | NFR-04 |
| UAT-16 已保存需求尚未关联仓库 | 从列表选中一条已保存但未关联仓库的需求，核对按新需求处理，工作类型只有「新功能」可用。分别尝试以「重构」「紧急修复」和「常规修复」启动，验证系统拒绝这些类型。选择流程并启动后，系统自动创建 Git 仓库，将其关联到所选需求和本次运行，并依次创建 `dev` 和 `feature` 分支。再次选中同一需求时，系统按已关联仓库的需求处理。 | BR-02、BR-13～BR-16、NFR-02 |
| UAT-17 已有仓库缺少 dev | 使用缺少 `dev` 的仓库分别验证新功能、重构和常规修复，覆盖默认分支名为 `main` 和 `master` 的情况。每种类型均先从该仓库设置的默认分支创建 `dev`，再分别从 `dev` 创建 `feature`、`refactor` 或 `fix`，并继续执行所选流程。 | BR-02、BR-16、NFR-02 |
| UAT-18 移除副负责人后尝试保存 | 对 Agent、流程和需求配置分别验证。副负责人打开编辑页并填写修改，主负责人将其移除。该用户在原编辑页点击保存，页面提示已被移除，提交被拒绝。主负责人重新打开配置时，看到的仍是上一次成功保存的内容。 | BR-23～BR-25、NFR-01 |
| UAT-19 主负责人转交 | 对 Agent、流程和需求配置分别验证。由当前主负责人向一名尚未担任该配置副负责人的已注册用户提交转交。提交成功后，在接任者进行任何操作之前，核对接任者已显示为该配置的主负责人、原主负责人已退出名单。接任者可添加或移除副负责人。原主负责人凭原身份尝试管理副负责人时，系统拒绝该操作。 | BR-23、BR-26 |
| UAT-20 多个 Agent 参与同一节点 | 为节点配置两个 Agent 并启动运行，核对两个 Agent 均实际参与执行，且可在处理节点任务时互相传递信息。验证节点内 Agent 能向用户发出问题并接收用户回复，用户可发送默认消息给协调 Agent，或通过 `@Agent` 指定收件 Agent，分别核对实际送达对象和回复。等待用户回复的行为见 UAT-21，失败场景随 DEC-09 定案补充。 | BR-09、BR-27 |
| UAT-21 单个 Agent 等待用户回复 | 为同一节点配置两个 Agent。Agent A 提问后，核对页面显示该问题、「等待回复」、回答框和「回复」按钮。用户提交前，核对 Agent A 等待、Agent B 继续执行独立任务。用户填写答案并点击「回复」后，核对答案交给 Agent A，且 Agent A 继续执行。 | BR-27、BR-28 |
| UAT-22 网页聊天连接本机 Codex CLI | 用户在有多台电脑可用的情况下，从电脑 A 发起配置了两个 Codex Agent 的运行，核对两个 Agent 均在电脑 A 上执行。用户在网页分别发送消息，核对电脑 A 上对应会话收到消息，网页显示各自回复。发起电脑关机后的恢复场景见 UAT-27。 | BR-10、BR-29 |
| UAT-23 同一聊天页面单人使用 | 发起人授权第二名注册用户后，两人同时进入时仅一人能操作。撤销后验证第二名用户的原页面和新请求均不能继续操作。 | BR-10、BR-30、NFR-01 |
| UAT-24 聊天页退出后立即释放 | 分别验证用户 A 导航离开聊天页和关闭聊天页的情况。每种情况下，另一名有权限的用户 B 随即打开同一聊天页，能立即进入并操作。 | BR-30 |
| UAT-25 聊天页断网后保留占用 | 用户 A 正在操作聊天页时模拟断网。从系统检测到断网时起计时。5 分钟内，用户 B 尝试进入时仍看到用户 A 占用的提示且无法操作，用户 A 重连后可继续操作。另测满 5 分钟仍未重连，系统释放占用，用户 B 可进入。 | BR-30、BR-31 |
| UAT-26 同一用户打开多个聊天标签页 | 用户在第一个标签页打开同一聊天并取得占用，再在第二个标签页打开。核对第一个标签页可以发送消息，第二个标签页无法操作。关闭第二个标签页时，第一个标签页仍可操作。另测关闭正在操作的标签页后，同一个聊天可从另一个标签页进入并操作。 | BR-30 |
| UAT-27 发起电脑关机后恢复运行 | 在电脑 A 上发起运行，执行中关闭电脑 A。通过另一台电脑查看该运行，核对页面显示「等待发起电脑上线」。电脑 A 重新上线且 CLI 可用后，核对系统自动继续原运行，运行标识保持一致。 | BR-29、BR-32、NFR-03 |
| UAT-28 需求默认仅创建者可见 | 用户 A 创建需求。同一项目内的用户 B 在需求列表、启动搜索和下拉列表中找不到该需求，直接打开需求详情时也无法查看。用户 A 将用户 B 添加为副负责人后，用户 B 可通过上述入口看到该需求，并可编辑和保存需求内容。 | BR-01、BR-23、BR-24、BR-33、NFR-01 |
| UAT-29 需求转交后原创建者失去查看权限 | 用户 A 创建需求，再将主负责人身份转交给用户 B。转交成功后，核对 B 可查看需求。A 在需求列表、启动搜索和下拉列表中找不到该需求，直接打开原详情链接时也无法查看。 | BR-26、BR-33、NFR-01 |
| UAT-30 需求发起权限 | 用户 A 为需求主负责人，用户 B 为副负责人。分别尝试用同一需求发起运行。核对 A 能启动，B 的发起请求被拒绝。 | BR-33、BR-34、NFR-01 |
| UAT-31 节点内 Agent 的执行先后 | 为同一节点配置两个 Agent 并设置 A 先于 B。核对 A 完成后 B 才开始。去掉先后配置并发起新运行，验证 B 可以在 A 完成前开始执行。 | BR-09、BR-27、BR-35 |
| UAT-32 需求副负责人无法参与运行聊天 | 需求主负责人发起运行。同一需求的副负责人在聊天页无人使用时尝试打开该运行的聊天页，系统拒绝进入。验证该副负责人发送消息或回复的请求也被拒绝。 | BR-36、NFR-01 |
| UAT-33 待回复问题保留至回复或取消 | Agent 提问后，当前用户关闭聊天页，等待一段时间后重新进入，核对同一问题仍为「等待回复」。核对有权限的用户提交答案后，原问题结束等待。取消权限与后续执行见 UAT-34。 | BR-28、BR-37 |
| UAT-34 发起人取消待回复问题 | Agent 提问后，另一名用户尝试取消，系统拒绝且问题仍为「等待回复」。运行发起人取消后，核对问题标记为「已取消」，提问的 Agent 结束等待并用已有信息继续执行。 | BR-28、BR-37 |
| UAT-35 结束节点校验与运行完成 | 分别尝试保存缺少结束节点的流程和结束节点未放在末尾的流程，核对系统拒绝保存并提示原因。将结束节点放在末尾，核对结束节点仅作为完成标记，配置中无 Agent 选项。保存并发起运行，核对运行在到达结束节点时标记为「已完成」。 | BR-12、BR-16、BR-38 |
| UAT-36 仅重试失败的 Agent | Agent A 成功而 B 失败。验证仅重试 B。另测人工跳过 B，保留处置记录且节点产物仍须满足门槛。越权操作被拒绝。 | BR-11、BR-39、NFR-02 |
| UAT-37 普通节点完成后才启动依赖节点 | 配置节点 B 依赖普通节点 A，A 配置两个 Agent。分别验证 A 仍有 Agent 未成功完成，以及两个 Agent 均成功但缺少 A 的节点产物，两种情况下 B 均保持等待。验证 A 的两个 Agent 均成功，其中一个 Agent 参与任务但未单独交付产物，A 已交付可引用的节点最终产物时，A 标记为完成，B 可开始。 | BR-16、BR-17、BR-40 |
| UAT-38 阶段按配置顺序执行 | 配置两个阶段，第二阶段的节点与第一阶段无显式依赖。第一阶段任一应执行节点尚未完成时，核对第二阶段保持等待。第一阶段的应执行节点全部完成后，核对第二阶段满足依赖条件的节点可开始。 | BR-16、BR-41 |
| UAT-39 结束节点等待所有并行路线 | 配置同阶段的两条路线，起点共同依赖一个上游节点，终点都通向同一个结束节点。第一条完成、第二条仍在执行时，核对运行尚未到达结束节点。第二条也完成后，核对运行到达结束节点并标记为「已完成」。 | BR-38、BR-41 |
| UAT-40 同阶段节点未满足并行条件 | 配置同一阶段两个互不依赖、没有共同上游且都可开始的节点，将 A 排在 B 前。核对 A 执行完成后才开始 B。保存相反的排列顺序并发起新运行，核对 B 执行完成后才开始 A。 | BR-41、BR-43 |
| UAT-41 同一上游完成后并行 | 配置同阶段节点 A、B，令它们分别直接依赖同一个上游节点 C，A 与 B 互不依赖。C 完成前两者均等待。C 完成且各自其他依赖满足后，验证 A 和 B 的执行时间可以重叠。 | BR-17、BR-40、BR-43 |
| UAT-42 循环依赖校验 | 配置 A 依赖 B、B 依赖 A，尝试保存并核对系统提示「有循环依赖」。再配置 A 依赖 B、B 依赖 C、C 依赖 A，核对同样拒绝保存。解除循环且其他规则均满足后可保存。 | BR-17、BR-44 |
| UAT-43 根据条件选择路线 | 在同一流程中配置「通过」和「需修复」各自对应的路线。分别运行两个场景，使上游节点的最终产物给出「通过」和「需修复」。核对每次运行只执行对应的一条路线。 | BR-16、BR-45 |
| UAT-44 条件分支必须配置两条路线 | 分别尝试只配置「通过」路线和只配置「需修复」路线，核对系统均拒绝保存，并提示缺少的路线。补齐两个结果对应的路线，且流程满足其他保存规则时可保存。 | BR-45 |
| UAT-45 修复后复查通过才允许发布 | 使检查结果为「需修复」并完成修复。分别验证尚未复查及复查结果仍为「需修复」时，发布均不开始。核对复查由原「检查」节点执行，且针对修复后的产物。复查结果为「通过」且满足其他适用发布条件后，验证发布可开始。 | BR-07、BR-46 |
| UAT-46 未达上限时自动再次修复 | 配置自动修复次数上限。首轮修复后，核对同一次运行重新执行原「检查」节点。复查仍为「需修复」且未达上限时，核对系统自动启动下一轮修复，修复完成后再次执行同一检查节点。 | BR-46、BR-47 |
| UAT-47 达到自动修复上限后等待人工 | 达到上限后，受影响路线及其依赖节点等待，符合执行条件的无关路线继续。最后一轮复查通过时，受影响路线可继续。 | BR-46、BR-47 |
| UAT-48 达到上限后的人工操作 | 自动修复上限为 3 次，达到上限且仍需修复后，核对当前聊天页操作者可以使用两个操作，其他用户尝试提交时被拒绝。由当前操作者选择「再修一轮」。核对同一次运行仅执行额外一轮修复和复查，仍需修复时再次暂停。选择「停止本次运行」，核对状态显示「已停止」且后续节点未开始。 | BR-46～BR-48 |
| UAT-49 检查节点独立计算修复上限 | 同一流程中检查节点 A 的上限设为 1，检查节点 B 的上限设为 3。A 完成一轮修复并复查通过后进入 B。核对 B 的首次修复从第 1 轮起算，并可按自己的上限自动修复至第 3 轮。 | BR-47 |
| UAT-50 检查缺少有效结果时等待人工 | 让检查节点产出没有检查结论的报告，另测报告结论无法识别的情况。核对两种情况下运行页面均显示「待人工处理」，说明缺少有效检查结果，「通过」和「需修复」路线均未开始。当前聊天页操作者点击「重新检查」，核对原「检查」节点在同一次运行中重新执行。得到有效结论后开始对应路线，再次缺少有效结论则继续等待人工。 | BR-45、BR-49 |
| UAT-51 启动后在需求阶段补齐描述 | 创建需求时仅填写名称，选择含需求阶段的可用流程并启动。运行到需求阶段后补填描述，核对需求内容已保存，后续阶段可引用该描述。 | BR-01、BR-13 |
| UAT-52 工作类型共用有权使用的流程 | 选择已关联仓库的需求，在启动入口分别选择四种工作类型。核对每种类型均可通过搜索和下拉选中同一组有使用权限的可用流程，无权限使用的流程始终无法选中。流程副负责人有启动权时可选该流程。另验 Agent 副负责人可在自己有编辑权的流程中选用该 Agent，撤权后不得再凭该身份选用，非负责人不出现在使用候选，直接提交同样拒绝。 | BR-14、BR-15、NFR-01 |
| UAT-53 无需求阶段的流程启动前须填描述 | 分别以新建需求和描述为空的已有需求选择没有需求阶段的流程，核对系统提示补齐描述，运行未启动。补齐描述后，满足其他启动条件时可以发起。 | BR-01、BR-13 |
| UAT-54 已有同名需求时选择原需求 | 用户 A 为「登录优化」需求的主负责人。A 在启动入口和需求配置入口分别尝试新建同名需求，核对系统提示选择已有需求，并阻止重复创建。选择已有需求后，使用的是原需求记录。另一用户在不同项目中尝试创建同名需求时，系统拒绝创建，仅提示名称不可用，不展示原需求或负责人。 | BR-13、BR-50、NFR-01 |

拟议验收条件为通过已批准的首期 `Must` 场景，完成试点环境和账号验证，确认账号注册登录、个人资料访问边界、三类配置的负责人权限、失败恢复职责及验收人。`Should` 场景按批准后的首期范围执行。UAT 日期与签署人待确认。
