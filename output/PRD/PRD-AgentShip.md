## 1. 概述

AgentShip 将用户选择的需求和流程转化为可跟踪的研发运行。需求主负责人在网页发起运行，系统准备 Git 仓库和分支，在发起电脑上运行 Codex Agent，并按流程交付产品定义、前后端代码、测试结果及发布记录。每个普通节点由协调 Agent 带领该节点选中的子 Agent 执行。用户可在看板查看进度、产物和阻塞原因，并通过网页回复问题或处理异常。发起电脑离线期间，其他电脑上的有权用户仍能查看同一次运行。

首期拟验证新需求从建仓到发布、已有需求使用原仓库继续交付，以及发起电脑离线后的续跑。四种工作类型的启动与分支规则均纳入验收。

## 2. 问题与机会

- **发起交付**。需求主负责人需要确定需求、工作类型、流程及正确的仓库与分支。交付进入不同阶段后，用户需要知道每一步采用了什么输入、由谁处理、产生了什么结果。
- **节点分工**。不同角色可以处理同一节点中的专业任务。用户需要知道哪个子 Agent 正在执行、在等待谁回复、失败后如何只重试该子任务，以及最终产物是否已可供下游使用。
- **执行中断**。运行依赖发起电脑。网页关闭、聊天断网、电脑离线和 Agent 执行失败各有不同的处理方式。产品需要让用户能判断当前情况及下一步操作。
- **证据与优先级**。问题与规则来自 BRD 和项目发起人。现有流程耗时、失败率、人力投入、用户规模和交付日期待试点确认。

## 3. 目标用户

| 角色 | 使用情境与目标 | 已确定的权限边界 |
|---|---|---|
| 注册用户 | 注册、登录，访问有权使用的业务页面。 | 可用邮箱或用户名搭配密码登录。 |
| 需求主负责人 | 建立或选择需求，发起运行，查看进度。 | 按提交时的现任主负责人身份判定发起权。 |

| 配置主负责人 | 创建和维护需求、流程或 Agent 配置，管理副负责人或转交配置。 | 创建时自动取得主负责人身份。 |
| 配置副负责人 | 协助查看和编辑已分配的配置。 | 需求副负责人可编辑需求，但无法用该需求发起运行或使用该需求的运行聊天。 |

| 项目维护者 / 发布验收人员 | 处理 Git 或外部执行异常，验证交付或发布。 | 人员范围、外部恢复及发布放行权限待定。 |

### 6.4 协调 Agent 与子 Agent

**角色库**是可选角色的集合。**节点配置**只包含该节点选中的角色。**协调 Agent**负责分工、协调和最终产物。**子 Agent**在各自的任务范围内执行并交回结果。首期按「角色库可用角色供节点按需选择，已选角色沿用既有完成门槛」编写。正常路径全部所选角色参与。失败 Agent 可由当前操作者按 FR-AG-05 处置。

| ID | 故事 | 优先级 / 决策状态 | 产品要求与验收 | 来源 |
|---|---|---|---|---|
| FR-AG-01 | US-05 | P0 / Confirmed | 普通节点可配置一名协调 Agent，并从已接入、可用且有权使用的角色库中按需选择子 Agent。产品支持选取任意所需的可用角色组合，选择数量可超过两个。保存重开后可核对角色清单，运行只分派该节点已选角色。验收至少选三个子 Agent，并留一个可用角色未选，核对实际分派与所选一致。 | BR-09、BR-27，2026-11-09 对话 |
| FR-AG-02 | US-05 | P0 / Confirmed | 协调 Agent 给已选角色分派有明确范围的任务。可配置子 Agent 的执行先后，未配置时按并行方式执行。验收三名以上子 Agent 的先后与并行安排，验证已选角色均获得任务。 | BR-27、BR-35，2026-11-09 对话 |

## 8. 技术考虑与依赖

- **Confirmed 技术约束**。已选 React + TypeScript、Java + Spring Boot、PostgreSQL 平台主库与 Java 本机执行程序。技术约束用于系统设计，产品规则继续以 BRD 为基线。

- **Confirmed 产品约束**。Codex CLI 在发起运行的用户电脑上执行，网页呈现消息、节点进度和人工操作。每次运行关联所选需求、流程、Git 仓库与分支。
- **Confirmed 角色库参考**。Skill Library 中的专业角色和协作模式用于定义可选择的子 Agent。仓库中已有 Codex 角色适配定义和通用 Agent Skill。每个角色须经本机可用性及权限确认后才作为可选项。 [Skill Library](https://github.com/zwong83/skill-library) · [Codex 角色适配](https://github.com/zwong83/skill-library/tree/main/adapters/codex/agents) · [协调者与专业角色交接规则](https://github.com/zwong83/skill-library/blob/main/agents/system-design-agent/references/specialist-coordination.md)
- **Proposed 接入方案**。使用本机 Codex App Server 承载会话，由协调 Agent 通过原生 spawn_agent 调用所选角色并转交角色之间的任务信息。原型优先验证三个以上子 Agent，例如角色库中的 architecture、interface_data、quality_attributes，并验证指定角色回复、仅重试失败角色、关闭网页后保留待答，以及本机重启后继续同一次运行。若原生子会话无法满足这些场景，评估由本机 App Server 的独立会话承载同一套子 Agent 角色。实现选择在技术方案中评审。 [OpenAI 子 Agent 文档](https://learn.chatgpt.com/docs/agent-configuration/subagents) · [OpenAI App Server 文档](https://learn.chatgpt.com/docs/app-server)
- **TBD 外部依赖**。Git 托管平台、仓库归属和访问权限，试点测试与发布能力，目标环境及放行人，兼容的 Codex CLI 版本和本机接入条件，均须在相应里程碑前确认。

## 12. 风险与处理

风险责任人和发生概率均待试点确认。

| 风险 | 影响 | 拟议处理 |
|---|---|---|
| 原生子 Agent 的会话控制达不到网页要求 | 等待的问题难以定向回复，恢复或单独重试可能失效。 | M1 先验证会话可识别、可续跑和失败隔离。必要时评估独立本机会话。 |
| 已选角色因本机容量或角色不可用而漏执行 | 节点被误判完成，后续产物缺失。 | 明确角色可用性、排队和失败状态，核对全部已选任务和节点最终产物。 |
| 多个子 Agent 同时修改同一交付物 | 结果冲突或有效内容被覆盖。 | 由协调 Agent 明确任务范围，发现冲突时等待处理后再交付节点产物。 |

| 确认后的需求变化影响已完成节点 | 下游使用旧产物，造成返工或验收不一致。 | 明确受影响节点的处理规则，记录本次执行采用的需求版本。 |
| 发布前置条件或试点环境未定 | 无法判断交付完成或正确放行。 | M0 指定环境、必测项和发布验收责任人。 |
